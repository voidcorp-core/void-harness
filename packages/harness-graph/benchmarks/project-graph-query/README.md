# ProjectGraph query benchmark

Run `pnpm benchmark:query` from the repository root. Ten isolated samples per query, each in its own
Node process, against one seeded corpus generated by `corpus.mjs`. Timing comes from
`performance.now()` around the query call; peak memory is the isolated process high-water mark from
`process.resourceUsage().maxRSS`. A sample whose query returns an empty answer fails the run, so a
timing can never be the timing of a no-op.

The corpus is synthetic on purpose: a published number has to be reproducible on another machine, and
no two checkouts of a real tree are the same graph. It carries the structures the queries actually
walk — intra- and cross-package imports, dynamic imports, a cycle inside every package, test coverage
edges, ownership, and rename lineage.

## DEV-439 baseline

Measured on 2026-08-05 with Node v24.15.0, Darwin 25.3.0, and an Apple M3. Corpus: 250 packages,
5,000 files, 6,140 nodes, 18,038 edges. p95 over ten isolated samples per query; `repeated` is the
per-call mean of 20 consecutive calls on one loaded snapshot.

| Query | cold p95 | repeated p95 |
|---|---:|---:|
| explain | 0.68 ms | 0.25 ms |
| path | 5.55 ms | 1.34 ms |
| impact | 7.15 ms | 1.59 ms |
| subgraph | 9.39 ms | 3.22 ms |
| owners | 1.46 ms | 0.40 ms |
| tests-for | 1.39 ms | 0.36 ms |
| staleness | 0.03 ms | 0.001 ms |

Peak isolated process RSS was 117,276,672 bytes (111.84 MiB), corpus construction included.

The executable gates require every cold and repeated p95 below 250 ms and peak RSS below 512 MiB.
They are engineering regression budgets for this corpus on one machine, not cross-machine product
guarantees. The budgets were chosen before the first measurement: a budget set from the first run
only proves that the first run happened.

## What these numbers do not cover

**Queries are not the cost of asking a question.** Every query here runs against a snapshot already
in memory. A `void-harness graph <query>` invocation first opens the store, which builds or
revalidates the ProjectGraph, and that is where the wall-clock goes. On this repository (1,633
indexed files) on 2026-08-05, one CLI invocation measured ~3.5 s, of which the queries above are
single-digit milliseconds.

Two facts behind that, both owned by extraction (DEV-436), not by this surface:

- A one-shot CLI process starts with a cold change journal, so it rescans and rehashes the tree.
  The incremental fast path is real (see `../project-graph/README.md`: 34 ms p95 for one changed
  file) but it needs a caller that keeps a journal across observations.
- The cache is published only when the build is `fresh`. This repository builds `partial` — 4
  oversized files and 3 unparseable sources out of 3,268 scanned — so no cache is ever published
  and every invocation pays the full cold build. Any project with a single generated artifact over
  the byte budget is in the same position.

**`repeated` is not a cache measurement.** The queries build their adjacency index per call by
design (`query.ts`), so a repeated run that stays close to a cold one is the expected result, not a
regression. It is measured to keep that cost model visible rather than assumed.
