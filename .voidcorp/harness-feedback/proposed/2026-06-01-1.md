# Trigger

While editing a `.tsx` component this session, `no-null-grep` blocked an edit
containing the idiomatic React pattern `return cond ? <Thing /> : null` (and a
bare `return null` guard). The recent fix `f15d513` ("comment- and string-aware")
correctly stops flagging `null` inside `//` comments, block comments, and quoted
strings — but a `null` used as a *render value* in JSX is none of those: it is a
bare identifier, so it survives the `sed` stripping and is still reported.

# Observation

`render → null` is the canonical React way to render nothing; it is not a
business-domain nullable. The hook's own header already concedes it is "a
line-oriented heuristic, not an AST", and that is exactly the limit being hit:
a per-line regex cannot distinguish "return null from a component" (legitimate)
from "let x: T | null" (the thing the rule wants to catch). The practical cost is
that component authors learn to sprinkle `// allow-null:` on render guards, which
trains the override into muscle memory and erodes the rule for the real cases.

# Proposed change

Cheapest, no new dependency: in `.tsx` files only, treat `null` as allowed when it
sits in a JSX-return position — i.e. the stripped line matches `return null`,
`return … ? … : null`, or a trailing `: null` / `? null`. Keep the existing
`// allow-null:` override for everything else. Better but heavier: replace the
regex with a tiny tree-sitter / TS AST check for `.tsx` so render-position nulls
are structurally exempt. Recommend the scoped-regex bypass now, log the AST option
as the eventual direction.

# Rationale

A hook that blocks an idiomatic, unavoidable React pattern produces false
positives on nearly every component file. False positives are the fastest way to
kill trust in a guard: users disable it or reflexively override it, at which point
it no longer catches the genuine domain-`null` it exists for. Scoping out the one
clearly-safe JSX position keeps the rule sharp where it matters.
