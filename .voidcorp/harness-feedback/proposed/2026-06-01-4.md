# Trigger

Running vitest against code that (transitively) imports `server-only` threw at
import time. The only fix applied was a per-test `vi.mock('server-only')`. There
is no global alias, so the mock has to be repeated in every test that touches a
server module — and it is easy to forget, producing a confusing red on otherwise
correct code.

# Observation

`server-only` is designed to throw outside an RSC bundler so server code can't
leak into a client bundle. vitest runs in Node, with no such bundler, so it hits
the throw. Per-test `vi.mock` is repetitive boilerplate and a forget-and-fail
trap. The standard fix is a single config-level alias of `server-only`
(and its sibling `client-only`) to a no-op module — via `resolve.alias` or a
shared `vitest.setup.ts` global mock — so tests "just work" without per-file
ceremony. This is exactly the kind of stack-vs-test-runner friction a stack pack
should absorb once, centrally.

# Proposed change

In `pack-nextjs`, ship a vitest config fragment that aliases `server-only` and
`client-only` to an empty/no-op stub (e.g. `resolve.alias` pointing at a tiny
`server-only.stub.ts`, or a `setupFiles` entry doing `vi.mock('server-only', () => ({}))`
plus the same for `client-only`). Document it in the pack so consumers inherit
working tests by default. Verify against current Next.js testing docs before
choosing alias vs setup-file.

# Rationale

A stack pack exists to absorb the known papercuts of its stack. Making every
consumer independently rediscover the `server-only` mock — and debug the cryptic
import-time throw the first time — is precisely the recurring toil the harness is
supposed to eliminate. Fix it once in the pack, not N times per project.
