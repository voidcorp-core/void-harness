# Trigger

While closing issue #17 cluster A (the loop git/allowlist hardening), the autoplan's
Codex reviewer surfaced a write path the secret-protection net never sees. It is
**pre-existing** and **wider than cluster A**, so it is logged here rather than
folded into that PR.

# Observation

`protect-sensitive-files` is registered as a `PreToolUse` hook on the `Edit|Write`
matcher only (see `packages/core/.claude-plugin/plugin.json`). It therefore never
inspects `Bash`. An agent with the (legitimately) allowed `Bash(cat:*)` /
`Bash(node:*)` can write a protected file straight past the deny-list:

```bash
cat > .env <<EOF
SECRET=...
EOF
node -e "require('fs').writeFileSync('.env', 'SECRET=...')"
printf '%s' "$X" > config/credentials.pem
```

None of these are an `Edit`/`Write` tool call, so `protect-sensitive-files` is not
invoked; the deny-list it enforces (`.env`, `*.pem`, ...) is silently bypassed.
The autonomous worker keeps `Bash(cat:*)` and `Bash(node:*)` in its allowlist (it
needs them for normal work), so the gap applies to it too.

# Proposed change

Add a Bash-aware layer that detects writes to protected paths via shell
redirection / heredoc and via `node -e`/`python -c` filesystem writes, and blocks
them with the same deny-list `protect-sensitive-files` already owns. Options:

1. Extend `protect-sensitive-files.sh` to also match the `Bash`/`shell` matcher and
   parse the command for `> <protected>`, `>> <protected>`, `tee <protected>`, and
   `-e/-c` writes — reusing the existing protected-path list.
2. Or add a focused `block-bash-secret-write.sh` PreToolUse(Bash) hook (one
   subject) wired alongside `block-dangerous-bash`.

Lean: option 1 keeps one subject ("never let a protected file be written"),
matching how `block-dangerous-bash` already handles both `Bash` and Codex `shell`.
Caveat: shell write detection is a heuristic (it will miss exotic forms), so it is
defense-in-depth, not a boundary — same posture as `block-dangerous-bash`.
