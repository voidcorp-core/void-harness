# Trigger

Following `void:tdd` in strict mode this session, the doctrine called for mutation
testing as part of the discipline. There is no Stryker (or equivalent) installed
in the harness or wired into the consumer, so the requirement is inapplicable:
there is nothing to run, and no gate enforces it.

# Observation

A doctrine that mandates a step the harness provides no way to execute is either
ignored (dead letter) or a source of low-grade guilt every time the loop is run.
The capability and the doctrine are out of sync. Note the gstack `mutation-testing`
skill already knows how to set up and run Stryker (full-project and diff-against-
main) — so the gap is integration, not knowledge: the doctrine asserts a gate the
shipped harness can't fulfil.

# Proposed change

Pick one and log it in `docs/DECISIONS.md`:

- **(a) Degrade honestly** — reframe mutation testing in `void:tdd` as a periodic
  / opt-in discipline (run before a release or on demand), not a per-change gate.
  Cheapest; keeps the doctrine truthful about what's enforced.
- **(b) Make it runnable** — a pack ships Stryker config + a
  `npx @voidcorp/harness` scaffold (or delegates to the gstack `mutation-testing`
  skill) so the gate has something to execute.
- **(c) Capability-detect** — the gate only fires when a `stryker.conf.*` is
  present; absent config means the step is skipped, not violated.

# Rationale

Doctrine that cannot be executed silently erodes trust in the entire decision
matrix — once one rule is known to be unenforceable, every rule is read as
optional. Either make mutation testing real (b/c) or make it honestly aspirational
(a); do not leave it asserted-but-impossible.
