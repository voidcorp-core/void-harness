# Declaring an autopilot block is the consent; there is no enabled flag

## Context

The program descriptor carried `autopilot.enabled`, a required boolean, and the
parser refused a block that did not state it: consent is never inferred. The
intent was right and the shape was not.

The block does not only carry consent. It carries `clusterSize`, `base`,
`mergeGate`, `verifyCommands` and the ownership partition -- everything autopilot
needs to run at all. Writing all of that and then setting `enabled: false` says
"I configured this and I do not want it", which nobody means. In practice the
field had exactly one useful value, and the other one was a way of leaving dead
configuration in a file.

It also cost a step at exactly the wrong moment. A project that wants autopilot
has to write the block and then remember one more line, and forgetting it
produces a refusal whose cause is a boolean rather than anything about the work.

## Decision

`autopilot.enabled` is removed. Declaring an `autopilot` block is the consent;
omitting it is the opt-out. There is no intermediate state.

## Consequences

Positive:

- Consent stays explicit and stays in the file, which is the property that
  mattered. It is now carried by the thing a person actually writes on purpose
  rather than by a flag beside it.
- One less field to get right, and one less way to configure autopilot fully and
  still have it refuse for a reason unrelated to the work.
- The opt-out becomes the absence of configuration, which is what an opt-out
  should look like. Nobody writes a block to disable the feature the block
  configures.

Negative:

- A project that wants to keep the configuration while pausing the feature has
  no field for it and must comment the block out or delete it. Accepted: pausing
  was never a stated need, and a commented block is a clearer signal than a
  boolean nobody reads.
- Existing programs carrying `enabled` need it removed. The parser refusing an
  unknown field would turn every current descriptor into an error, so it is
  ignored rather than rejected during the transition.

## Alternatives considered

- **Default the field to `true` and keep it optional.** Rejected, and it is the
  tempting one because it is two lines: a program that never mentioned autopilot
  would silently gain autonomous selection. The consent would then genuinely be
  inferred, which is the property this whole area exists to protect.

- **Keep the boolean.** Rejected: it is configuration whose only useful value is
  the one everybody sets, standing between a project and the feature it already
  described in full.

- **Ship a program template or example file so the flag is pre-filled.**
  Rejected: it adds a file to every project to work around a field that should
  not exist, and an example nobody reads is clutter that ages.

## Reversal cost

Low. Reintroducing the field means requiring it again in one validator and
restoring one line in each sister doc. No data migrates, and a descriptor written
without it is still valid input to the version that requires it, once the line is
added back.
