# Set Node 24 LTS as the floor for every package

## Context

Since 2026-07-23 the published CLI `voidharness`, the packs, the graph kernel and
the private apps have declared `engines.node >=22.12`, while CI and maintainers
ran Node 24. That gap was accepted so a Node 22 user could install without an
`engine-strict` failure. On 2026-09-21 the
[machine floor ADR](./2026-09-21-machine-node-24-lts-floor--89f1ec74-3cf3-492a-be98-2ec03c924508.md)
raised the private Void Machine package alone to `>=24.15.0`, leaving two floors
in one repository.

The [Node release schedule](https://github.com/nodejs/Release/blob/main/schedule.json)
on 2026-09-21: Node 22 has been in maintenance since 2025-10-21 and reaches end
of life on 2027-04-30; Node 24 is Active LTS until 2026-10-20, then maintenance
until 2028-04-30; Node 26 is Current and enters LTS on 2026-10-28. The latest
releases are [24.21.0](https://nodejs.org/en/blog/release/v24.21.0) and
[26.9.0](https://nodejs.org/en/blog/release/v26.9.0). The
[26.0.0 notes](https://nodejs.org/en/blog/release/v26.0.0) remove legacy
`_stream_*` modules, `http.Server.prototype.writeHeader()` and
`--experimental-transform-types`, and deprecate `module.register()` at runtime;
the repository uses none of them.

The toolchain does not force the floor: the
[Vitest 5 migration guide](https://vitest.dev/guide/migration/) requires Node
`>=22.12.0` and Vite `>=6.4.0`, and the TypeScript 7 compiler package declares
Node `>=16.20.0`. The decision is about the supported runtime, not a build
requirement.

## Decision

Every package in the monorepo, including the published CLI `voidharness`,
`@voidcorp/harness-graph` and the packs, declares `engines.node >=24.15.0`, the
same floor as Void Machine; `@types/node` follows the floor's major (24.x);
esbuild and tsup emit for `node24`. CI tests on Node 24 and adds Node 26 only to
the jobs where a second major can find a different failure.

## Consequences

Positive:

- One declared floor, equal to what CI proves, instead of a floor nobody tests.
- Node types match the lowest runtime, so an API newer than the floor is a type
  error rather than a runtime surprise on a Node 24 host.
- Emitted bundles target the floor instead of Node 20 and 22.
- Node 26 regressions are seen before 26 becomes the LTS line in October.

Negative:

- Breaking for consumers still on Node 22: npm warns on install, and a consumer
  with `engine-strict=true` cannot install. Released with a `BREAKING CHANGE`
  footer, so release-please cuts a major and the changelog names it.
- Node 22 is still supported upstream until 2027-04-30; its users must upgrade
  seven months before its end of life.

## Alternatives considered

- Keep `>=22.12` for the published packages and raise only private code:
  rejected by the maintainer. It keeps two floors and a declared range that CI
  never exercises, which is the drift the 07-23 decision already accepted once.
- `>=24.0.0`: accepts early 24.x builds nobody tests, and a second number next to
  the Void Machine floor.
- Require Node 26: it is Current until 2026-10-28, and nothing in the code needs it.
- Test every CI job on both 24 and 26: doubles the cost of jobs such as install
  conformance, whose result depends on the operating system, not the Node major.

## Reversal cost

Low for the declaration: lower `engines`, `@types/node` and the emit targets,
then run the full suite on Node 22. It rises as code starts relying on Node 24
APIs, which the matching `@types/node` now lets the type checker accept.
