# Set Node 24 LTS as the Void Machine floor

## Context

Void Machine alone currently declares Node >=22.12. The package uses Node's
filesystem, crypto, child process and ESM primitives and runs Vitest 4. Node
24.21.0 is Active LTS on 2026-09-21; Node 26.9.0 is Current until its planned
October LTS transition. TypeScript 7 and Vitest 5 warrant an explicit supported
runtime and a two-major test matrix. Other packages and the CLI retain their own
floors; this decision changes only `packages/void-machine`.

The [Node 24.21 release](https://nodejs.org/en/blog/release/v24.21.0),
[Node 26.0 release](https://nodejs.org/en/blog/release/v26.0.0), and
[Node 26.9 release](https://nodejs.org/en/blog/release/v26.9.0) were reviewed
against those primitives. The [Vitest 5 migration guide](https://vitest.dev/guide/migration/)
requires Node >=22.12, so it does not force the higher floor.

## Decision

Set Void Machine's Node engine floor to >=24.15.0 and verify the package under
Node 24 and Node 26. Keep the package's TypeScript and Node types explicit and
independent of the consumer pack's compiler configuration.

Node 24.15.0 is the first 24.x release where `node:sqlite` is a release candidate
according to the [Node 24 SQLite documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).
The higher floor removes the unavailability at Node 22.12 that motivated the
[21 September file-journal ADR](./2026-09-21-machine-note-mission-file-journal--5450858b-e832-40f2-a066-1f176dda6f5f.md).
It does not change the journal or prove SQLite's suitability for mounted volumes.
Storage remains a separate decision.

## Consequences

Positive:

- A maintained LTS floor and current-major verification bound the supported runtime.
- The package can evaluate native SQLite later without the old availability blocker.

Negative:

- Node 22 hosts cannot run this private package after the change, even though the
  repository's other packages may continue to support Node 22.
- The file journal remains in use; its process-crash and power-loss limits remain.

## Alternatives considered

- Retain Node 22.12: avoids a floor change but carries an older runtime and the
  SQLite availability gap while the foundation is still private.
- Require Node 26 now: shortens the matrix but makes a Current release mandatory
  before its LTS transition, with no package primitive requiring that jump.
- Set >=24.0.0: includes early 24.x builds where SQLite had a less mature
  experimental status; >=24.15.0 gives a meaningful LTS baseline.

## Reversal cost

Low before public distribution: lower the package engine and re-run the complete
contract suite on Node 22. Any future storage choice using `node:sqlite` would
raise that cost and need its own compatibility and migration decision.
