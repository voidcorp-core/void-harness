# Split pure mission transitions from durable execution

## Context

The note mission proved durable resume and cancellation, but its application module
owned revisions, transitions, outcome uncertainty, and note-specific record schemas
together. A second vertical would have to copy the lifecycle or teach the note
module about its stages. The foundation plan assigns pure transitions to `core/`,
durable driving to `runtime/`, record formats and admission to a vertical, and
composition to `application/`. Historical `note-mission/1` and `/2` bytes remain
readable and writable under their existing rules.

## Decision

Split the mission lifecycle into a pure, bounded reducer in `core/mission.ts` and
an injected journal driver in `runtime/mission.ts`; provide steps, value admission,
and record codecs from each vertical, and assemble them in the application.

The reducer accepts explicit events only and owns their legal order. The runtime
records a dispatch intent before an effect, fences concurrent writers with the
journal's expected revision, and never replays a dispatched step whose outcome is
unknown. The vertical codec owns schema versions and the meaning of accepted
values. The note codec preserves both historical formats; no new durable format
is introduced. The file journal remains the current adapter.

The package export remains doctor-only. These mission contracts stay private until
the plan's later contract-stabilization milestone.

## Consequences

Positive:

- A second three-step test vertical uses the same reducer and driver without a
  production-core change, including resume, cancellation, abandonment, and races.
- Each piece of lifecycle state has one owner and the note format stays compatible.

Negative:

- The generic driver has type parameters and a codec boundary; verticals must supply
  precise schemas and admission rules.
- The file journal retains its documented power-loss limits and lacks automatic
  reconciliation of unknown native effects.

## Alternatives considered

- **Keep lifecycle in the note application and copy it per vertical:** rejected
  because duplicated fencing and cancellation logic would drift under crashes.
- **Move all persistence and formats into a large core:** rejected because the
  core would import I/O or domain schemas and lose a single owner per concern.
- **Introduce a workflow framework or public extension API now:** rejected because
  one production vertical and one test vertical do not justify a frozen surface.

## Reversal cost

Medium: move the private driver behind another composition or replace its journal
port, then replay the same legacy fixtures and race contracts. The note records
do not need migration; changing them would require a separately versioned format.
