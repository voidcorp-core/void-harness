# Consumer-facing brand names are read under the current and every former name, written under the current one

## Context

The product is renamed from void-harness to void-machine (DEV-908 for the repository, the package
and the commands). Three things carrying the old brand live in consumer projects, where a release
cannot rewrite them: the managed blocks the installer writes (`<!-- void-harness:begin -->` in
CLAUDE.md and AGENTS.md, `# void-harness:begin` in `.gitignore` and `.git/info/exclude`,
`<!-- void-harness:context-continuity:begin -->` in `.void/machine/checkpoint.md`), and the
`VOID_HARNESS_*` settings people export in their shell or CI. A release that only knew the new
names would append a second managed block beside every old one, lose the resume state of every
interrupted session, and silently drop every override a person had set.

## Decision

The identity source declares, beside the current brand, the former marker namespaces and the
former environment prefixes; every read accepts any of them, every write uses the current one, and
an old block is replaced where it stands.

- `PRODUCT_IDENTITY.markers` derives the begin and end pair of each managed block for the current
  namespace and each former one (`current`, `recognized`). `managed-block.ts` in hook-runner is the
  single finder: it replaces the first recognized block with the new one and drops any other, so a
  file never carries two. The CLAUDE.md patcher and the ignore-file patcher both go through it.
- The mission engine parses the checkpoint but owns no brand. It exposes `checkpointCodec(markers)`
  and the hook runtime binds it to the identity once (`lifecycle/checkpoint-codec.ts`); the CLI
  reads checkpoints through the same binding. A begin of one namespace closed by an end of another,
  or one block under each name, is ambiguous and left untouched, as two blocks under one name were.
- `productSetting(env, name)` is the only reader of a product setting: the current prefix wins
  whenever it is set, even to an empty string; a former prefix is read only when the current one is
  absent.
- Mission event sources (`void-harness:mission.*`) keep their value. They are a wire format written
  into every consumer's run journal and compared on read; renaming them is an event-store migration,
  not a brand change, and nobody reads them as the product's name. The private root package keeps
  its name too, and the deprecated command keeps its own bin, both declared.

## Consequences

Positive:

- `init` or `update` from any 3.x install converges on one block under the new name, with the
  project's own text around it untouched, and keeps every override.
- A future rename appends one namespace and one prefix to the identity; no reader changes.

Negative:

- Every former name stays recognized until someone decides to drop it: an entry in
  `markers.deprecated` or `environment.deprecated` is a promise not removed lightly.
- A setting read under a former prefix emits no notice. A hook runs on every tool call, and a
  warning there would be noise; the documentation names the new prefix.

## Alternatives considered

- A one-shot migration step in `update` that rewrites every marker and prints the settings to
  rename: it misses the checkpoint written by a hook between two updates, the files of a clone that
  never runs `update`, and a CI that exports the old prefix; reading both costs nothing per call.
- Let the mission engine import the identity file: its build emits from `src/` only, so the file
  would be outside its root, and a pure engine that knows the product's name is the coupling this
  package exists to avoid.
- Rename the mission event sources with the rest: every in-flight mission would refuse its own
  earlier events after the upgrade, for a string no person reads.

## Reversal cost

Low. Dropping a former name is one line in the identity; the readers keep working with fewer pairs.
