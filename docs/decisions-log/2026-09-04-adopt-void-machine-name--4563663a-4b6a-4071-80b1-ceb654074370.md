# Adopt Void Machine as the product and CLI name

## Context

`void-harness` describes the mechanism but not the executable product, and it is weak as a distinct
market category. `void-agent` overstates one persona while the product coordinates runtimes, skills,
memory, tools and proofs. The name must communicate a dependable system that does work.

## Decision

Adopt **Void Machine** as the working product name, `void-machine` as the intended CLI and package,
and **Void Workbench** as the reserved name for its future control surface.

Public cutover waits for package, domain and trademark checks. The current `voidharness` package
becomes a bounded migration bridge rather than a second product.

## Consequences

Positive:

- The name conveys an executable, dependable whole rather than a library or one agent.
- Workbench preserves the craft metaphor for the interface without weakening the core product name.

Negative:

- Documentation, repository, package and commands need a coordinated compatibility migration.
- The package name being currently unused does not itself provide trademark clearance.

## Alternatives considered

- **Void Harness**: technically accurate, rejected as the primary brand because it sounds like a
  library and collides conceptually with an existing software delivery company.
- **Void Agent**: rejected because the product supervises agents and deterministic machinery rather
  than being one agent.
- **Void Workbench**: retained for the UI, rejected as the primary product because it underplays the
  autonomous runtime.

## Reversal cost

**Medium before public cutover, High after it.** Contracts remain name-agnostic, but package and
command compatibility require redirects and deprecation windows once users adopt them.
