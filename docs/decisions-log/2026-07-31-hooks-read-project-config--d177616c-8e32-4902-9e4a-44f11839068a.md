# Enforcement rules read the project's own configuration

## Context

Two enforcement rules blocked writes a consumer project had explicitly permitted.

`no-console` refused `tooling/compile.ts` in a project whose `biome.json` turns `noConsole` off for `tooling/**`, and whose neighbouring files are full of the calls it was refusing. The hook carried its own hardcoded allowlist — `scripts/`, tests, generated — and read no configuration at all. It was not enforcing "no console"; it was enforcing "no console except in `scripts/`", a rule nobody had written down and no project had agreed to.

`boundary-direction` refused imports of `@repo/db` from packages that legitimately depend on it, on the strength of a hardcoded star topology: "a package may import only itself or `@repo/core`". The project's own `docs/ARCHITECTURE.md` declared the edge legitimate. It also matched only `^packages/`, so a monorepo using `_modules/` received no enforcement while being told it had some. The only way through was an `allow-boundary:` comment per line — and a rule whose normal use is being suppressed is not a rule.

The common failure: a hook that doubles a linter the project already configures, without reading that configuration, does not enforce the project's rule. It imposes a second one with veto power.

## Decision

An enforcement rule that overlaps a tool the project already configures reads that configuration before blocking and defers to it; where no configuration exists, the harness floor still applies.

## Consequences

Positive:

- A project's own decisions hold. `no-console` honours `biome.json`, including per-path overrides and their precedence.
- `boundary-direction` stops inventing a topology and starts catching something real — an import of a workspace package the importer does not declare, which resolves today only through hoisting and breaks when the sibling that hoisted it changes.
- The rule now works outside `packages/`, so `_modules/`, `apps/` and any other layout are covered.
- `allow-boundary:` becomes an escape hatch again rather than the normal path.

Negative:

- Rules now do file I/O, where they were pure functions of their edits. Reads are memoised per path within a call and fail soft, but the purity is gone.
- Only Biome is understood. An ESLint or oxlint project gets the harness default, which may still overrule it — the same defect, narrowed rather than eliminated.
- A project can now weaken a harness rule by turning off the linter rule it mirrors. That is the intended trade: the alternative is the harness deciding it knows better than the project about the project.

## Alternatives considered

- **Add a harness-side config listing exemptions.** Rejected: the project already declared this once, in the file its linter reads. A second declaration would drift from the first, and the drift would be silent.
- **Keep the star topology and require projects to declare their graph.** Rejected: the dependency graph is already declared in every `package.json`. Asking for it again is asking a project to repeat itself so a hook does not have to read.
- **Drop the overlapping rules entirely and let the linter do it.** Tempting, and it would remove the conflict at the root. Rejected because the linter runs after the write and the hook runs before it; the floor exists for projects with no linter at all.
- **Fail closed when config cannot be read.** Rejected: a hook that throws on an unparseable config blocks every write in the repository. Failing loud for the wrong reason is worse than missing one console call.

## Reversal cost

Low. Both rules keep working without a project root and simply stop deferring; reverting is removing an argument.
