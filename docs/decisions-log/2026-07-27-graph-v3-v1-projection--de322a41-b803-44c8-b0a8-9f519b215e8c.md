# Adopt Graph v3 behind a read-only v1 projection

## Context

The v1 catalog is used by Graph Studio, status, certification, audit, and the bundled consumer
artifact. Mission and evidence data need stronger provenance and integrity contracts, but replacing
the v1 shape in one release would couple the new graph foundation to a Studio migration and make
rollback unsafe.

## Decision

Make the validated node-link v3 envelope the canonical build boundary, while projecting
CatalogGraph v3 through a read-only v1 adapter for every current v1 consumer until those consumers
migrate deliberately.

## Consequences

Positive:

- Catalog, Mission, Evidence, and future Project graphs share one integrity and provenance model.
- Existing Studio, analyzers, certification, and bundles keep their current behavior.
- Invalid snapshots and deltas are rejected before any compatibility projection.
- `catalog.v3.json` and `model.json` can be compared during a staged migration.

Negative:

- The integration writer regenerates and ships two catalog artifacts during the compatibility window.
- Every v1 read pays a bounded validation and in-memory adaptation cost.
- The legacy `KERNEL_VERSION = 1` remains until the final v1 consumer is removed.

## Alternatives considered

- Break all v1 consumers in the same change. Rejected because it combines a data migration with a
  visual product migration and removes a safe rollback path.
- Keep v1 authoritative and add ad hoc fields. Rejected because MissionGraph and EvidenceGraph need
  semantics that the catalog-only contract cannot express safely.
- Let readers accept either shape without validation. Rejected because malformed, stale, or
  path-escaping graph data could become authoritative silently.

## Reversal cost

Medium. Rolling back removes `catalog.v3.json` and restores direct v1 reads without changing the v1
artifact. After consumers begin persisting v3 deltas, reversal requires retaining the v3 reader or
performing an explicit data migration.
