# Approved six-ticket delivery scope

Folpe approved the bounded pool DEV-531, DEV-610, DEV-611, DEV-630, DEV-682 and
DEV-645, including the two choices below, on 14 September. On 15 September he
required the process-proof failures to be corrected before this pool resumed,
with regression prevention retained. This records that existing authorization;
it does not authorize another production promotion or add backlog work.

## Outcomes and boundaries

| Unit | Requested outcome | Boundary |
| --- | --- | --- |
| DEV-531 | Contextual motion guidance and a dedicated core skill | Functional feedback stays short; expressive sequences require an observable narrative purpose. Reduced motion preserves information; content never depends on animation. No video pipeline or mandated library. |
| DEV-610 | Declared decisions and invariants in the project graph, with why and provenance | Use the existing knowledge-system spec; no inferred declarations, new graph engine or hardcoded historical ADR count. |
| DEV-611 | Opt-in Git regeneration of knowledge | Reuse the existing builder. Checkpoint functionality is already delivered. No automatic staging, amend or follow-up commit. |
| DEV-630 | An actionable update proposal from the agent | Approved option 1: offer once per session and wait for explicit permission before update. Preserve detection, cache and marketplace silence. |
| DEV-682 | Reuse existing doctrine sections without duplicates | Explicit semantic routing, no fuzzy matching. Preserve marketplace behavior and narrow the historical claim by supersession. |
| DEV-645 | An honest rollback failure message | Co-edited manifest handling is already delivered. Preserve accepted fingerprint policy; describe persistent layout repair accurately. |

Full provider-native issues and their current relations remain the executable
units. The linked [coordination plan](../plans/2026-09-15-approved-six-ticket-cluster-plan.md)
records work boundaries and proof requirements. The existing
[knowledge-system spec](2026-08-17-project-knowledge-system.md) supplies the
DEV-610/611 domain context; completed checkpoint work is not reopened.

## Execution constraints

At most two writers, each in its own worktree, with independent review capacity.
Only disjoint declared ownership may run in parallel; generated assets and shared
CLI/graph paths remain sequential. DEV-611 follows integration of DEV-610.
The same test-first, security, source-grounding and regression gates apply in a
batch as to a single ticket. No worker pushes, merges or changes tracker progress.

The Git hook for DEV-611 runs after commit: if regenerated versioned knowledge
changes, the working tree can become dirty and the output must say so. It does
not claim that the previous commit or its CI already contains that artifact.

## Completion evidence

Every unit needs its acceptance criteria, applicable real-consumer or runtime
proof, fresh tests and independent review. Integration requires the full suite
and CI on the reviewed tree, with a clean base and no bypass. Linear owns mutable
claims, blockers and completion. Promotion to main remains a human decision.
