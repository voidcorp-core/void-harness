# merge

## Résumé

`implement` s'arrête à la PR ouverte, `autopilot` produit une PR d'intégration, et rien ne dit
comment vider la file. Le geste est fait à la main, et il a l'air trivial jusqu'au moment où il ne
l'est pas.

Une skill `merge` prend la file des PR ouvertes, décide de l'ordre, refuse ce qui n'est pas
mergeable, résout ce qui n'est mécanique, et boucle jusqu'à ce que la file soit vide ou bloquée.

## Problème

Le 2026-08-19, sept PR ont été mergées à la main dans ce dépôt. Un « merge tout ce qui est vert »
aurait échoué sur les quatre cas suivants, tous rencontrés dans la même session.

| Cas rencontré | Ce qu'un merge naïf aurait fait |
|---|---|
| La PR de promotion `develop` -> `main` est verte et mergeable en permanence | Déclencher une release non voulue |
| #236 réparait le workflow dont l'absence la mettait en conflit | Rester bloquée indéfiniment, ou être forcée |
| Trois PR étaient vertes mais `BEHIND` | Merger une base périmée, ou échouer sans comprendre |
| Les conflits portaient sur des artefacts générés | Choisir un côté, donc livrer un artefact faux |

La cause commune : l'état d'une PR ne se lit pas dans sa couleur. Il se lit dans sa relation aux
autres, à sa base, et à la nature de ce qui entre en conflit.

## Le modèle

### Ce qui n'entre jamais dans la file

Une PR qui existe pour rester ouverte. Dans ce dépôt, c'est la promotion permanente : la merger
est la seule décision de contenu du cycle de release, et elle appartient à un humain. La skill la
liste et la laisse, en disant pourquoi.

Une PR en brouillon, et une PR dont l'auteur n'est pas la personne qui lance la skill sans que
celle-ci le dise explicitement.

### L'ordre

Pas la date, pas le numéro : **le déblocage**. Une PR dont le contenu supprime la cause du conflit
d'une autre passe avant elle. À défaut de relation, l'ordre est celui du moindre conflit : ce qui
se merge sans rien toucher passe d'abord, ce qui demande une résolution attend son tour.

### Le feu vert

Trois conditions, toutes nécessaires : la CI est **verte**, la branche est **à jour** avec sa
base, et le merge est **propre**. `BEHIND` n'est pas un feu vert : les checks ont tourné sur une
base qui n'existe plus. Remettre à jour, réattendre la CI, puis merger.

La skill n'a pas besoin d'un hook pour l'empêcher de merger du rouge : la protection de branche
côté serveur le refuse déjà, et un hook local devrait appeler le réseau pour connaître un état que
seul GitHub détient. Le garde-fou existe, il est au bon endroit.

### La résolution

Deux natures, une seule automatisable.

- **Mécanique** : le conflit porte sur un artefact généré. On le **régénère** depuis les sources
  fusionnées, jamais on ne choisit un côté. Un artefact choisi est un artefact faux, qui passe la
  CI et ment ensuite.
- **De contenu** : deux intentions se croisent. La boucle s'arrête et le dit. C'est un travail
  d'auteur, pas de file d'attente.

Un cas mixte, où un fichier généré porte aussi une décision (une version dans un manifeste), est
traité comme du contenu : le sens de la valeur décide, pas son emplacement.

### La boucle

Tant qu'une PR devient mergeable, la traiter et recommencer : merger l'une rend les autres
`BEHIND`, donc la file bouge à chaque tour. Elle s'arrête quand plus rien ne progresse, et rend
alors ce qui reste avec, pour chaque PR, la raison exacte du blocage.

## Ce que la skill ne fait pas

- Elle ne relit pas le code. Une PR est supposée revue ; la skill décide de mécanique, pas de
  qualité.
- Elle ne force jamais un merge, ne passe jamais `--admin`, ne réécrit jamais une branche protégée.
- Elle ne merge pas la promotion de release, quelle que soit sa couleur.

## Tests

TDD strict sur les fonctions pures : l'ordonnancement d'une file donnée, la classification d'un
conflit, la décision de feu vert à partir d'un état de PR. Ce sont des entrées de données et des
verdicts, exactement ce qui se teste sans réseau.

Souple sur l'enveloppe qui appelle `gh` et rend le rapport.

## Écarté

- **Un hook qui refuse `gh pr merge` sur CI rouge.** Il devrait interroger GitHub, donc mettre du
  réseau dans le plancher d'enforcement, pour dupliquer une garantie que la protection de branche
  donne déjà côté serveur.
- **Merger par ordre de numéro ou d'ancienneté.** L'ordre correct est celui du déblocage, et il
  n'a aucun rapport avec la date : la PR la plus ancienne du jour était celle qui devait passer en
  dernier.
- **Résoudre un conflit de contenu au jugé.** C'est ce qui produit un merge vert et faux.
